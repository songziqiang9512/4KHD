# 4KHD 开发错误路径备忘

> 日期：2026-05-01
> 目的：记录这轮开发中已经验证不稳定、低效或方向错误的路径，避免后续重复踩坑。

## 当前目标边界

这个软件的核心目标不是复刻 4khd.com 的网页，而是让用户在自己的 macOS 应用里稳定浏览站点内容：

- 左侧 / 中间负责栏目、列表、翻页和内容分类。
- 右侧是主体验，必须优先保证大图清晰、可快速切换、可缩放、可保存。
- 数据要能区分普通图集、推荐内容、广告内容，但这个判断应来自站点结构和抓取结果，不应靠标题猜测。
- 列表和详情可以来自 Apify 抓取数据，但图片展示必须尊重真实网页加载上下文。

## 已证明是错误或高风险的路径

### 1. 把图片 URL 当成普通静态资源直连

错误做法：

- 用 `URLSession`、`curl` 或原生图片组件直接请求 `i0.wp.com/...webp?w=1300`。
- 把 `previewURL/fullsizeURL` 当成最终可靠图片地址。
- 在保存功能里直接下载当前图片 URL。

实际问题：

- `i0.wp.com` 图片直连会出现 400。
- `pic.4khd.com` 原始资源链路也可能出现 TLS、代理或证书问题。
- 图片 URL 在 JSON 和 HTML 里存在，不代表原生 HTTP 客户端可以稳定读取。

正确方向：

- 图片展示主链路应通过 `WKWebView` 的真实页面上下文完成。
- 先打开真实详情页，再从 DOM 中提取图片节点。
- 保存功能也不能简单复用 `URLSession`，需要单独验证浏览器上下文下载、`WKDownload`、缓存资源或其他可落盘方案。

### 2. 只把单张图片塞进 WebView

错误做法：

- 不打开真实详情页，直接生成一段 `<img src="...">` HTML 交给 `WKWebView`。
- 认为只要是 WebKit 渲染，就等同于真实网站加载。

实际问题：

- 单张图片 HTML 缺少真实详情页的来源、跳转链路、页面上下文和站点加载行为。
- 这种方式有时能显示，有时不能显示，表现不稳定。
- 失败时容易误判成 UI 布局问题，实际是资源加载上下文不对。

正确方向：

- 右侧详情页必须先 `load(URLRequest(detailURL))` 打开真实子页面。
- 等 `didFinish` 后执行 JS，从 `.entry-content`、`.wp-block-post-content`、`article`、`main` 或 `body` 里提取图片。
- 提取后可以在同一个 `WKWebView` 里重写成纯图片显示页，但前提是已经进入过真实详情页。

### 3. 把 WebKit 当成整套 UI

错误做法：

- 直接把站点页面嵌进应用，当作主界面。
- 用网页原有布局承担列表、详情、推荐、广告区分等产品能力。

实际问题：

- UI 可控性差，无法满足三段式图片浏览软件的体验。
- 右侧大图不是第一优先级，用户切图、缩放、保存都不顺。
- 广告、推荐、正文图集混在站点页面里，应用层难以做清晰信息架构。

正确方向：

- 应用主界面必须是原生自定义 UI。
- WebView 是图片加载和页面解析辅助层，不是产品界面本身。
- 列表、详情标题、页数、图数、推荐 / 广告标记应进入应用自己的数据模型。

### 4. 运行时依赖项目目录里的 Apify 输出

错误做法：

- App 运行时直接读 `/Scripts/outputs/4khd_site_capture`。
- 认为开发目录存在就等于应用沙盒内可访问。

实际问题：

- macOS App Sandbox 打开后，应用不能稳定读取项目目录。
- 开发机上能读，不代表打包后能读。
- Xcode 的文件同步资源可能被扁平化放进 `Contents/Resources` 根目录，不能只写死子目录路径。

正确方向：

- 关键 Apify JSON 和详情 HTML 要进入应用 bundle。
- 读取 bundle 资源时同时兼容根目录和 `ApifyCapture` 子目录。
- 项目目录路径只能作为开发回退，不应是正式主链路。

### 5. 把 Apify 结果当成最终图片加载方案

错误做法：

- 认为 Apify 抓到了 `sampleImageURLs`，应用就可以直接显示全部大图。
- 用 Apify 的图片 URL 跳过真实详情页。

实际问题：

- Apify 结果适合做结构化索引：标题、详情链接、封面、页数、图数、样例图片。
- 图片 URL 本身仍然受站点图片代理和上下文限制。
- 只依赖样例 URL 会让右侧大图、保存和翻页都变得不可靠。

正确方向：

- Apify 负责列表、详情元信息和离线兜底。
- 右侧图片显示仍要以真实详情页 DOM 提取为准。
- Apify 中的 URL 可以作为 fallback，不应作为唯一真实来源。

### 6. 每次切图都重新打开详情页

错误做法：

- 用户点下一张时重新加载详情页。
- 缩略图每个格子都独立打开一次详情页。

实际问题：

- 切图速度明显变慢。
- 同一详情页会被重复解析。
- 多个 `WKWebView` 同时加载会带来额外网络、内存和时序问题。

正确方向：

- 一个详情页打开一次后，应缓存本页提取出的图片 URL 列表。
- 切换图片只切换 index，不重新跑完整详情页。
- 缩略图应尽量复用同一份提取结果，后续需要做共享缓存或预热，而不是无限创建独立 WebView。

### 7. 详情分页不能无脑回到第一页缓存

错误做法：

- 无论请求的是 `...html` 还是 `...html/2`，都返回本地 `detail-{id}.html`。
- 自动加载下一页时仍然拿第一页 HTML 解析。

实际问题：

- UI 看起来在翻页，实际图片仍然来自第一页。
- 到最后一张自动加载下一页时会重复内容。
- 页数、图数和当前图片 index 会逐步错位。

正确方向：

- 本地详情 HTML 只能代表它实际抓到的那一页。
- 当请求 URL 带 `/2`、`/3` 这类分页后缀时，应读取对应分页抓取结果，或回退到远程真实详情页解析。
- 自动加载下一页前必须确认新页数据不是第一页重复数据。

### 8. 只看 HTML 字符串解析，不看真实 DOM

错误做法：

- 只用正则从原始 HTML 里找 `<img>`。
- 只从一个主内容选择器里提取图片。

实际问题：

- 站点会使用 `picture`、`currentSrc`、`data-src`、`data-lazy-src`、`a[href] > img` 等多种形式。
- 有些真实大图在链接 href 上，不一定只在 img src 上。
- 主内容选择器失配时会得到空详情，造成右侧无图。

正确方向：

- 静态 HTML 解析只能做结构兜底。
- 真实显示链路应在浏览器 DOM 中提取：`a[href] > img`、`picture img`、`figure a[href] img`、普通 `img` 都要覆盖。
- 提取后按允许 host 过滤：`pic.4khd.com`、`img.4khd.com`、`i0.wp.com`。

### 9. 自动加载不能只靠简单 onAppear 哨兵

错误做法：

- 缩略图或详情底部出现一个透明 `Color.clear`，一出现就加载下一页。
- 不区分用户真实滚到底、布局首次渲染、数据刷新和重复触发。

实际问题：

- 可能页面刚打开就提前加载下一页。
- 可能重复请求。
- 也可能在快速切图时错过触发。

正确方向：

- 自动加载下一页要有明确状态：当前页、总页数、是否正在加载、是否已经请求过。
- 缩略图滚到底和大图切到最后一张可以触发同一套 ViewModel 方法。
- 触发后必须合并新页图片，并保持当前选中 index 不错乱。

### 10. UI 优化不能优先于数据主链路

错误做法：

- 在大图还不稳定时先大改布局。
- 把图片加载失败误认为是视觉层问题。

实际问题：

- UI 改动会掩盖真实问题来源。
- 右侧大图无法显示时，布局再合理也没有意义。
- 用户实际需要的是图片浏览器，不是网页信息面板。

正确方向：

- 先保证数据链路：列表、详情、真实页面打开、DOM 抽图、大图显示。
- 再优化三段式 UI：导航、列表、右侧大图、缩略图、操作按钮。
- 每次 UI 调整后必须亲自启动应用验证右侧大图，而不是只看构建通过。

## 后续实现优先级建议

1. 稳定右侧真实详情页抽图链路。
2. 做详情页级别的图片提取缓存，避免每次切图和每个缩略图重复开页面。
3. 接上自动加载下一页：缩略图滚到底和大图切到最后一张都走同一入口。
4. 重新设计保存功能，不再假设 `URLSession` 能直接下载图片 URL。
5. 在抓取层补强广告 / 推荐 / 正文内容的结构化标记。
6. 最后再做性能优化、预加载和本地缓存。

## 判断原则

以后遇到 4KHD 图片显示问题，先按这个顺序排查：

1. 应用是否真的打开了详情页 URL。
2. `didFinish` 后 DOM 里是否能提取到图片。
3. 提取到的是不是允许的图片 host。
4. 当前显示的是不是同一个 WebView 上下文。
5. 是否错误地走回了 `URLSession` 或本地第一页缓存。

不要先从布局、颜色、按钮或 SwiftUI 刷新问题入手。这个项目目前最容易误判的点，是把图片上下文问题看成 UI 问题。

## 2026-05-02 从零重建后的补充结论

这次已把旧源码完整归档到 `/Users/songziqiang/Documents/Development/4KHD-legacy-archive-20260502-043229`，当前项目源码从零重建。后续不要再从旧归档里复制实现，只能用它查历史。

新的主链路应保持简单：

1. Apify `expanded-ui-content.json` 是列表和结构事实源：栏目、标题、详情 URL、封面 URL、总图数、总页数、分页 URL、样例图。
2. 应用 UI 是三段式：左侧栏目，中间图集列表，右侧大图和缩略图。
3. 右侧大图必须加载真实详情页 URL，在页面 DOM 里找到目标图片节点，并移动这个已加载节点作为大图显示。
4. 不要把 `i0.wp.com` 或 `pic.4khd.com` URL 放进自建 HTML 再显示。实测 `i0.wp.com` 可返回 400，`pic.4khd.com` 直连有证书风险。
5. 不要 clone 图片节点后重新设置 `src`，这会触发新请求，又回到直连图片的坑。应移动原页面中已经加载成功的 `img` 节点。
6. 切换下一张时必须重置 WebView 协调器的“正在显示图片”状态，否则会停留在原网页，不会重新聚焦目标图。
7. 列表封面和缩略图暂时不要用独立 WebView 逐个加载真实图片，这会造成大量并发页面/图片请求。先保证右侧主图稳定，再补封面缓存。

当前最小验证结果：

- `xcodebuild -scheme 4KHD -configuration Debug -destination 'platform=macOS' build` 通过。
- 新 app 能打开 Apify 列表，显示三段式布局。
- 右侧首张大图已验证能通过真实详情页上下文显示。
- 继续切图和跨页自动加载仍要作为下一轮重点验证。

## 2026-05-02 继续验证后的补充

新增已验证坑：

- 不要把真实页面里的图片节点移动到新建容器里再覆盖全屏。这样会破坏原 DOM，下一张图可能找不到，或者图片节点重新布局后黑屏。
- 不要用 fixed 黑色遮罩强行盖住页面，再把未完成加载的图片放到最上层。图片未完成时会出现整块黑屏。
- 同一详情页内切图不要重新加载详情页。应复用当前 WebView 和已提取的图片列表，在页面内重新定位目标图片。

当前更稳的做法：

1. 加载真实详情页。
2. DOM 提取该页图片列表并缓存。
3. 当前图片只在原页面中增强样式并滚动到可视区域，不移动节点、不直连下载。
4. 保存先保存当前 WebView 快照 PNG，避免回到 `URLSession` 直连图片 URL。
5. 每个详情页先建立 20 个图片槽位，翻到页尾再追加下一页分页 URL 的槽位。

当前限制：

- 大图已能稳定显示和同页切换，但还不是完全纯净的“独立图片画布”；仍保留部分网页上下文。
- 保存是当前可视快照，不是原始最高分辨率文件。
- 跨详情分页自动加载还需要继续做实机验证。
