# 4KHD 自定义 UI + WebView + 脚本接入可行计划框架

## 1. 文档目标

本文档用于给后续开发提供一份可执行的技术路线参考，目标不是立刻做正式产品实现，而是先明确：

- 哪些能力已经验证可行
- 哪些链路当前不稳定
- 第一阶段应该如何落地
- 后续如何逐步从实验方案演进到可维护的软件能力

当前目标站点以 `4khd.com` 为例，重点验证方向是：

- 使用自定义 UI 展示站点内容
- 使用脚本抓取结构化数据
- 使用 `WebView` 负责复杂图片加载
- 为后续 macOS 软件接入做准备

---

## 2. 当前已验证结论

### 2.1 已经验证可行的部分

- 页面 HTML 可以抓取
- 列表页和详情页结构可以解析
- 详情页分页规则可以识别
- 图集图片 URL 可以完整枚举
- 单个图集可导出完整图片 URL 列表

以页面：

- `https://www.4khd.com/content/20/pudding-dafa-jk-sailor-suit.html`

为例，当前已经验证：

- 图集总页数：`7`
- 图集总图数：`126`
- 图片文件名存在稳定编号规律：
  - `...-001.webp`
  - `...-002.webp`
  - ...
  - `...-126.webp`

### 2.2 已验证不稳定的部分

- 直接用普通 HTTP 客户端请求 `i0.wp.com` 代理图时，返回 `400`
- 尝试反推 `pic.4khd.com` 原图地址时，返回 `526`

这说明：

- “页面结构解析” 和 “图片直连下载” 是两件不同的事
- 当前更适合采用：
  - 脚本负责结构化抓取
  - `WebView` 负责真实浏览器环境加载图片

---

## 3. 推荐总体方案

推荐采用三层结构：

1. 采集层
2. 视图层
3. 浏览器辅助层

### 3.1 采集层

职责：

- 抓取列表页 / 详情页 HTML
- 解析标题、链接、分页、图片数量、下载入口
- 为 UI 层输出结构化数据

建议产物：

- JSON 数据
- 分页图片 URL 清单
- 详情页索引数据

### 3.2 视图层

职责：

- 提供完全自定义的宫格卡片 UI
- 展示标题、数量、时间、封面、标签、详情入口
- 做筛选、搜索、分页、收藏等交互

这部分不需要复用对方网页 UI。

### 3.3 浏览器辅助层

职责：

- 用 `WKWebView` 或同类浏览器内核加载站点页面
- 利用浏览器环境拿到真实图片显示结果
- 处理普通 HTTP 客户端难以稳定请求的资源

这部分建议作为后台资源解析器，而不是直接暴露为主界面。

---

## 4. 推荐技术路线

### 路线 A：自定义 UI + 脚本解析 + WebView 辅助加载

这是当前最推荐的路线。

#### 核心思路

- 脚本抓结构
- App 用自己的数据模型和 UI
- `WebView` 只负责最难的图片加载

#### 优点

- UI 完全可控
- 数据结构清晰
- 可逐步加缓存
- 对站点图片代理机制更友好

#### 缺点

- 需要维护脚本和 App 的桥接
- 需要在 App 内部管理 `WebView` 生命周期

### 路线 B：纯脚本抓取 + 原生直接拉图

不建议作为第一阶段主路线。

#### 原因

- 当前图片代理链路已表现出不稳定
- 直连图片失败率较高
- 后续维护成本和兼容成本高

### 路线 C：完全 WebView 驱动

可以做，但不适合作为最终产品形态。

#### 适合场景

- 快速做验证版
- 快速确认页面真实加载行为

#### 问题

- UI 可控性差
- 难做你自己的信息架构和宫格设计

---

## 5. 第一阶段建议目标

第一阶段不追求“彻底下载原图”，重点做：

1. 稳定浏览
2. 稳定展示
3. 稳定结构化

### 第一阶段范围

- 列表页解析
- 详情页解析
- 图集分页枚举
- 自定义宫格卡片 UI
- 点击卡片进入自定义详情页
- 详情页内部由 `WebView` 辅助加载图片

### 第一阶段不建议强做

- 后台批量裸拉全部图片
- 在没有浏览器环境的前提下强做稳定缩略图下载
- 把实验性抓取逻辑直接变成正式产品核心依赖

## 6. 数据模型建议

建议先定义统一的数据模型。

### 6.1 列表卡片模型

```json
{
  "id": "pudding-dafa-jk-sailor-suit",
  "title": "布丁大法 JK水手服[387MB-126photos]",
  "detail_url": "https://www.4khd.com/content/20/pudding-dafa-jk-sailor-suit.html",
```

## 7. 图片加载建议

### 7.1 建议采用分级回退

第一层：

- 直接尝试已有展示图 URL

第二层：

- 如果失败，交给隐藏 `WKWebView` 加载详情页

第三层：

- 在 `WKWebView` 中注入 JS，收集页面真实图片节点

第四层：

- 必要时对图像区域截图或缓存渲染结果

### 7.2 不建议的做法

- 默认假设 `i0.wp.com` 图片 URL 可以用普通网络层稳定拉取
- 在没有浏览器环境的情况下把图像请求做成核心能力

---

## 8. `WKWebView` 接入建议

### 8.1 建议角色

`WKWebView` 不作为主 UI，而作为：

- 图片加载辅助器
- 详情页资源读取器
- 页面脚本执行器

### 8.2 建议能力

- 加载详情页 URL
- 等待页面完成加载
- 注入 JS 读取：
  - `document.images`
  - gallery 容器
  - 当前页图片 URL
  - 分页信息
- 将结果传回原生层

### 8.3 与原生 UI 的边界

- 原生层负责：
  - 卡片布局
  - 筛选搜索
  - 缓存策略
  - 导航与交互
- `WebView` 负责：
  - 高兼容性加载
  - 真实浏览器上下文中的图片读取

## 9. 建议开发阶段划分

### 阶段 1：结构采样版

目标：

- 抓列表
- 抓详情
- 解析分页
- 导出图集 JSON

验收：

- 能稳定得到图集标题、详情页、分页、图数、下载入口

### 阶段 2：自定义 UI 浏览版

目标：

- 做宫格卡片展示
- 读取 JSON 数据渲染
- 点击进入自定义详情页

验收：

- 用户能在你自己的 UI 中浏览内容

### 阶段 3：WebView 图片辅助版

目标：

- 用 `WKWebView` 获取图片显示结果
- 构建卡片封面和详情图加载回退策略

验收：

- 图片显示明显比裸拉 URL 更稳定

### 阶段 4：缓存与性能版

目标：

- 加本地缓存
- 降低重复加载
- 做失败重试和占位图

验收：

- 二次浏览更快
- 失败展示可控

当前已形成这些实验脚本，可作为后续参考：

- `scripts/4khd_image_probe.py`
  - 用于列表页 / 详情页采样
- `scripts/4khd_gallery_dump.py`

这些脚本目前适合做：

- 数据源验证
- 接入前采样
- 页面结构变化监测

不建议直接把它们原样作为正式产品链路核心。

## 11. 风险与注意事项

### 技术风险

- 图片请求可能依赖真实浏览器环境
- 图片代理或源站链路可能变化
- 页面结构未来可能调整

### 产品风险

- 不应把实验脚本直接当正式生产能力
- 图片加载失败时必须有 UI 降级方案

### 维护建议

- 保留页面结构探测脚本
- 定期抽样检查字段稳定性
- 将“结构解析”和“图片加载”解耦

---

## 12. 推荐结论

基于当前验证结果，推荐的后续开发路线是：

- 自定义 UI 做主界面
- 脚本负责结构解析
- `WKWebView` 负责复杂图片加载
- 第一阶段优先完成“可浏览、可展示、可解析”
- 第二阶段再优化图片加载稳定性和缓存

这条路线比“纯脚本裸拉图片”更现实，也更适合作为软件长期演进的基础。
